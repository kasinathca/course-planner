# FFCS Studio — implementation handoff (requirements baseline v0.2)

**Purpose:** build a future-proof, deterministic, fully offline FFCS/degree planner for VIT Vellore, beginning with the Integrated M.Tech CSE (Data Science), admission batch 2024–25. This bundle is a specification and handoff, **not** a completed application or a fully verified university rulebook.

## Product boundary

- **Daily driver:** a browser-based local website served on `http://127.0.0.1:8765` by Python FastAPI/Uvicorn. It runs course browsing, planning, validation, timetable search and ranking entirely on the laptop. No desktop shell or Node runtime.
- **Capture companion:** a small Tampermonkey userscript operates **only when the user is already signed in on VTOP**, reads displayed course allocation pages, saves a local export, and never registers subjects or collects credentials.
- **Optional legacy compatibility:** import/export FFCSinator-style data; no dependency on its Node/Next.js server.
- **Only discretionary AI:** cleaning an unusual PDF/Excel import if deterministic parsers cannot handle it. No model, token or cloud service required in normal operation. A localhost HTTP API is explicitly allowed for communication with the Python backend.

## Acceptance principle

A top-ranked plan can never contain a time clash, broken cross-component pairing, duplicate course, or breached **hard** constraint. If required information is missing, it is explicitly shown as `unverified` or `unknown`, not silently invented. Numerical schedule counts are only displayed when generated by a correct counting algorithm, never extrapolated from sampled plans.

## Implementation sequence

Make **an import-and-validation vertical slice first**, then implement the time rules, then a reference brute-force solver, then an optimized solver and simple UI, then degree integration, then VTOP userscript/export polishing, then FFCS live assistance. Do not spend the first phase on a polished hero dashboard.

## Deliberate non-goals

No automated FFCS registration, no credential scraping, no bypassing rate limits, no **remote** server-side synchronization, no cloud persistence, no automatic faculty rating claims, no invented class schedules from course credits, no Node runtime for the new application. The local Python server is explicitly in-scope.

**Maintainer note:** the user's historical FFCSinator clone and source dumps should remain in a separate `legacy/` directory if copied into the implementation repository; omit `node_modules`, `.next`, tokens, saved sessions, and build outputs.
