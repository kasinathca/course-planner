# FFCS Studio — Codex working agreement (local-browser edition, v0.4)

Read `docs/00_START_HERE.md`, `docs/10_IMPLEMENTATION.md`, `docs/12_PHASES_AND_CODEX.md`, and `docs/16_LOCALHOST_RUNTIME_AND_SECURITY.md` before writing code; then read all remaining documents, schemas and sanitized examples. User's final interface decision overrides older wording: **a local website at `http://127.0.0.1:8765`**, NOT PySide6, Qt, native desktop, Electron, Node, or a public/cloud website.

**Approved implementation**: Python 3.12+ with FastAPI and Uvicorn for a local HTTP server; SQLite; plain HTML, CSS and modern vanilla JavaScript ES modules served as static files, with no Node, npm, build tooling, CDN or remote runtime requests. Jinja2 server-rendered HTML is permitted. The local API is allowed; *external* APIs and hosted services are prohibited. Python packages may need to be installed once while online; subsequent operation must be offline. Windows 11 is the initial target.

Core rules: no invented faculty, section pairing or official time mapping; retain every raw source row; unknown slots fail strict planning. Keep domain/solver independent of HTTP/UI and write pure Python tests. VTOP collection is a separate safe Tampermonkey userscript that captures only displayed course/category/table data after user selection and exports files; no portal automation, credential scraping, or registration automation. Do not commit private portal HTML, auth tokens, databases, virtual environments, generated build output, `node_modules`, `.next`, or student-identifying data.

Phase 3 solver rules: use the complete candidate source, never the display-limited preview; preserve exact calendar/offering/revision/allocation identity; distinguish strict verification from explicit exploratory assumptions; keep exact counting separate from bounded top-K; revalidate every emitted timetable; and run CPU search/count work only in bounded cancellable processes. Never present an incomplete count as exact or a resource-limited ranking as globally optimal.

The verified baseline is maintained on `main`. For each explicitly requested future phase: fetch the latest `origin/main`, create a descriptive feature branch, implement the complete phase, run pytest/Ruff/Mypy/dependency checks and an appropriate localhost browser test, update README and the phase engineering report, audit staged files for secrets and generated artifacts, commit the verified implementation, fast-forward local `main` when safe, push `main` normally, verify the remote SHA and clean tree, preserve the feature branch, and stop before the next phase. Never force-push, rewrite published history, delete remote data, or publish incomplete/failing work. Normal non-force pushes of completed and verified phases to the existing repository are authorized by the user; destructive remote actions require separate approval.
